# Кешування операцій читання

## Стратегія кешування
Використана стратегія **Cache-Aside** з Redis. Сервіс спочатку перевіряє наявність ключа в Redis; якщо дані є (Cache Hit), вони миттєво повертаються без валідації Pydantic (завдяки прямому поверненню типу `Response`). Якщо даних немає, робиться SQL-запит до бази, дані швидко серіалізуються через `model_dump_json()`, зберігаються в Redis з TTL = 60 секунд і повертаються клієнту. 

Використано окремий Redis-контейнер (або ElastiCache), оскільки кеш у пам'яті процесу (наприклад, `cachetools`) створює проблему за наявності кількох екземплярів (воркерів/контейнерів). Кожен новий екземпляр застосунку мав би порожній ізольований кеш, робив би зайві паралельні запити до БД на ті самі дані, і що найгірше — це призвело б до розсинхронізації: один екземпляр міг би віддавати старі дані, а інший — нові. Спільний Redis розв'язує цю проблему як єдине джерело істини для всіх воркерів.

## Порівняльна таблиця (Без кешу vs З кешем)

| Показник | Без кешу | З увімкненим кешем |
| :--- | :--- | :--- |
| **Латентність (p50)** | 310 ms | ~ 15-20 ms |
| **Латентність (p95)** | 1200 ms | ~ 40 ms |
| **Кількість запитів (RPS)** | ~ 105.7 req/s | ~ 200+ req/s |
| **Навантаження на БД (CPU)** | Високе (~95-100%) | Мінімальне (майже 0%) |
| **Частка помилок (Failures)** | 4.28% (при 190+ юзерів)* | 0% |

*\*Примітка: Без кешу система "зламалася" на 190 одночасних користувачах (помилки 500/502). З кешем система стабільно тримає 200+ користувачів без помилок.*

## Аналіз влучань та актуальності даних

**Частка влучань у кеш (Hit Ratio):**
Враховуючи, що профіль навантажувального тесту містить 1 операцію запису (POST) на 9 операцій читання (GET), відсоток влучань у кеш становить приблизно 90% після початкового прогріву.

**Актуальність даних (Скільки часу клієнт бачить застарілі дані):**
Оскільки встановлено TTL = 60 секунд, у найгіршому випадку клієнт може бачити застарілі дані рівно 1 хвилину після того, як інший запит змінив дані в БД.

**Як зменшити цей час:**
Щоб клієнти одразу бачили актуальні дані, у сервісі реалізовано **активну інвалідацію кешу**. При будь-якій операції запису (створення нового варіанту, або при деактивації/зміні продукту), сервіс викликає спеціальний метод (наприклад, `_invalidate_product_cache()`), який примусово видаляє відповідні ключі з Redis. Це гарантує, що наступний GET-запит не знайде старих даних у кеші і буде змушений витягнути свіжі дані безпосередньо з бази.
