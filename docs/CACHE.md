# Кешування операцій читання

## Стратегія кешування
Використана стратегія **Cache-Aside** з Redis. Сервіс спочатку перевіряє наявність ключа в Redis; якщо дані є (Cache Hit), вони миттєво повертаються без валідації Pydantic (завдяки прямому поверненню типу `Response`). Якщо даних немає, робиться SQL-запит до бази, дані швидко серіалізуються через `model_dump_json()`, зберігаються в Redis з TTL = 60 секунд і повертаються клієнту. 
Використано окремий Redis-контейнер (або ElastiCache), оскільки кеш у пам'яті процесу (`cachetools`) був би неефективним: кожен новий екземпляр застосунку мав би порожній кеш і робив би зайві запити до БД, що спричинило б розсинхронізацію даних між воркерами.

## Порівняльна таблиця

| Показник | Без кешу (або до масштабування) | З увімкненим кешем |
| :--- | :--- | :--- |
| **Латентність (p95)** | ~ 1500 - 2700 ms | ~ 40 ms |
| **Кількість запитів (RPS)** | ~ 100 req/s | ~ 190+ req/s |
| **Навантаження на БД (CPU)** | Високе (~95-100%) | Мінімальне (майже 0%) |

## Аналіз влучань та актуальності даних
**Частка влучань у кеш (Hit Ratio):**
Враховуючи, що профіль навантаження містить 1 запис на 9 читань (і читання ідуть за обмеженою кількістю шляхів), відсоток влучань у кеш становить приблизно 90% після початкового прогріву.

**Актуальність даних:**
З базовим TTL у 60 секунд клієнт може бачити застарілі дані максимум 1 хвилину після зміни.
Щоб зменшити цей час до нуля, у сервісі реалізовано **активну інвалідацію кешу**. При створенні нового варіанту двигуна чи кольору, або при деактивації продукту, сервіс викликає метод `_invalidate_product_cache()`, який видаляє ключі з Redis через `scan_iter`. Це гарантує, що наступний запит на читання одразу підтягне свіжі дані.
