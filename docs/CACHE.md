# Кешування читань

## Реалізація

Список товарів використовує cache-aside: ключ формується з нормалізованих фільтрів, Redis hit повертає серіалізований результат, miss читає PostgreSQL і записує результат із TTL **60 секунд**. `CACHE_ENABLED=false` вимикає читання та заповнення кешу для контрольного прогону. Зміни товару видаляють ключі списків і detail cache; за помилки Redis сервіс переходить до бази.

У Terraform Redis — sidecar контейнер у кожній ECS task. Це недороге рішення для лабораторної, але кожна task має окремий Redis і власний hit-rate; cache entries не спільні між екземплярами. У виробництві слід використовувати спільний приватний Redis, із TLS/auth, мережевими правилами, моніторингом і планом витрат. Sidecar є ephemeral cache без потреби у persistence.

## Порівняння

| Режим | p95 | Запити/с | Навантаження PostgreSQL | Cache hit rate |
| --- | ---: | ---: | --- | ---: |
| Без кешу (`cache_enabled=false`) | Потрібен контрольний прогін | Потрібен контрольний прогін | Потрібно зняти метрику RDS CPU/DatabaseConnections | 0% |
| З кешем (`cache_enabled=true`) | Потрібен контрольний прогін | Потрібен контрольний прогін | Потрібно зняти метрику RDS CPU/DatabaseConnections | Потрібні Redis counters |

Попередній Locust прогін не дає чесного A/B порівняння: змінений код кешу не був розгорнутий із вимірюваннями hit/miss і навантаженням RDS. Не заповнюйте ці клітинки оцінками. Запустіть однаковий сценарій і тривалість спершу з `cache_enabled=false`, потім з `true`; після кожного прогону зафіксуйте CloudWatch RDS метрики та Redis `catalog:metrics:products:hits` / `catalog:metrics:products:misses` з усіх активних task sidecar Redis. Hit rate = hits / (hits + misses). Перед серією видаліть ці два лічильники з кожного Redis, щоб виміряти лише поточний прогін.

## Актуальність і межі

TTL обмежує максимальну застарілість списку приблизно 60 секундами. Успішні операції зміни товару інвалідовують кеш списків і detail. Якщо інвалідація не вдасться, обмежений TTL усе одно зрештою оновить значення; для жорсткішої узгодженості потрібен спільний кеш і надійне invalidation/outbox. Ключі мають версію `v1`, щоб зміну формату кешованих даних можна було безпечно розділити.

Для уникнення cache stampede на популярних ключах можна додати короткий Redis lock/single-flight і jitter до TTL. Тут TTL однаковий для всіх ключів, тому одночасне завершення кількох гарячих ключів можливе.
